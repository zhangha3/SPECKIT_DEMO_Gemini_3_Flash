## 用户场景与测试 *(必填)*

### 用户故事 1 - 港口搜索与展示 (优先级: P1)

作为一名航运操作员，我希望在一个简洁的搜索框中输入信息，系统能够自动判断我是按代码查还是按名查，并快速展示中英文详细信息。

**优先级原因**: 这是核心功能，决定了系统的基本可用性。

**独立测试**: 在单一搜索框中输入 "CNSHA" 或 "上海" 或 "Shanghai"，点击查询后应能从 JSON 数据中找回对应条目。

### 验收场景**:

1. **Given** 页面已加载, **When** 在搜索框输入 "CNSHA" 并点击查询, **Then** 系统判定为精确查询，列表中仅展示 "上海 (Shanghai)"。
2. **Given** 页面已加载, **When** 输入 "Shang" 并回车, **Then** 系统判定为模糊查询，列表中展示 Name CN 或 Name EN 包含 "Shang" 的港口，且按代码 A-Z 排序，每页 10 条。
3. **Given** JSON 数据源损坏或不可用, **When** 页面初始化, **Then** 页面展示错误提示，且搜索框与查询按钮处于禁用 (Disabled) 状态。


---

### 用户故事 2 - 初始数据加载与健壮性 (优先级: P2)

系统启动时应自动加载港口数据，若加载失败应有明确提示。

**优先级原因**: 确保系统具备开箱即用的可用性且对异常有基本处理。

**独立测试**: 模拟 JSON 文件丢失或损坏，验证页面是否显示报错提示。

**验收场景**:

1. **Given** 系统启动, **When** JSON 文件包含 5 个主流港口, **Then** 页面初始状态应显示这 5 个港口的概览或准备好被搜索。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统提供单一搜索框。应根据输入内容自动切换模式：输入为 5 位字母时执行港口代码精确匹配；否则同时在中文和英文名称字段中执行模糊匹配。
- **FR-002**: 搜索必须显式触发，仅在用户点击“查询”按钮或在搜索框按下回车键（Enter）时执行。
- **FR-003**: 港口信息展示项必须包括：港口代码 (Port Code)、中文名称 (Name CN)、英文名称 (Name EN)、所属国家 (Country)、所属时区 (Timezone)。
- **FR-004**: 查询结果必须支持前端分页展示（默认 10 条/页），且列表默认按港口代码 (Code) 字母升序排列。
- **FR-005**: 系统必须能优雅处理数据加载失败的情况：若 JSON 文件加载异常，应展示明确的错误提示并禁用搜索交互。
- **FR-006**: 数据源存储在本地 JSON 文件中，包含并支持中英文双语搜索及展示。

### 关键实体

- **港口 (Port)**: 代表一个全球航运节点。
  - `code` (String): 港口代码，遵循 UN/LOCODE 规范（5位字母）。
  - `name_cn` (String): 港口中文名称。
  - `name_en` (String): 港口英文名称。
  - `country` (String): 所在国家名称。
  - `timezone` (String): IANA 时区标识符（如 Asia/Shanghai）。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 在包含 100 个港口的 JSON 数据下，搜索响应时间（从点击到渲染）应小于 500 毫秒。
- **SC-002**: 核心查询功能（代码精确、名称模糊）在主流浏览器下 100% 可用。
- **SC-003**: 90% 的用户能够在无需说明指导的情况下，10秒内找到目标港口的 UN/LOCODE。

## 假设与约束

- **假设**: 初始 JSON 数据将包含至少上海 (CNSHA)、新加坡 (SGSGP)、鹿特丹 (NLRTM) 等主流港口。
- **约束**: 暂不涉及后端数据库，所有数据逻辑在前端内存或本地逻辑中。
- **UI 风格**: 遵循简洁、现代的 UI 设计原则，不绑定具体技术框架。

## 术语表 (Feature Specific)

- **UN/LOCODE**: 联合国贸易和运输地点代码。
- **模糊查询**: 指搜索关键词只需包含在目标文本中即可匹配。
